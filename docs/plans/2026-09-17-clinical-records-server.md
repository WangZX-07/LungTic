# LungTic 病例服务器与分级访问计划

状态：阶段 0 与阶段 1 的同步上传 MVP 已实现；阶段 2 的限时会诊授权已实现，申请审批、版本追溯和阶段 3 待做。分支：`feat/clinical-records-server`。运行说明见 [中心病例服务](../CLINICAL_SERVER.md)。

## 目标与边界

在现有 FastAPI、MySQL、Vue/Electron 结构上增加可部署到医院内网的中心服务。医师可以上传与其负责患者相关的 DICOM、TICI 和病历附件；获授权的诊疗团队成员可以读取；科主任可以读取其**本科室诊疗范围内**的患者记录。病例文件存于受控文件或对象存储，数据库保存索引和授权关系。独立的本地 TICI 查看器继续支持离线查看，但导入中心病例库时必须走同一套服务端授权。

当前分支实现了第一版服务，但不接入真实患者数据，也不把病例文件、密钥或数据库备份放入 GitHub。部署位置、医院组织结构、保存期限和患者告知方式由实际合作医疗机构确认。

## 代码现状与阻断问题

- 主服务已有 `backend/main.py`、MySQL 模型、JWT 登录及 DICOM/NIfTI/TICI 上传；`backend/viewer_main.py` 是另一个绑定本机的 SQLite 查看服务。因此要扩展现有后端，而不是从零新建 API。
- `backend/routers/dicom.py` 中医生和管理员可列出、读取所有患者；`backend/routers/tici.py` 对医生和管理员也放行全部检查。现有 `patients.user_id` 主要用于关联患者账号，不能表示主管医师或科室。
- 分割、IGTV 和轨迹路由按 `study_id` 读取检查，尚无统一的患者级授权。DICOM/NIfTI 上传可用输入的患者编码查找已有患者，但没有先验证上传者对该患者的写入权限。
- 当前没有通用病历附件、科室、诊疗团队、会诊授权、访问审计或安全的文件版本管理。
- 现有默认管理员密码、开发用 JWT 密钥、宽泛 CORS、浏览器 `localStorage` 令牌及服务器加载用户上传的 `.pth` 模型，均需在允许远程访问前处理。

## 权限规则

统一采用“角色 + 组织范围 + 患者关系 + 临时授权”的服务端判定，默认拒绝。页面隐藏按钮仅用于界面体验，不能代替 API 校验。

| 身份 | 默认可见范围 | 允许操作 |
| --- | --- | --- |
| 主管/诊疗医师 | 有效诊疗团队分配的患者 | 查看、上传和补充其患者记录；删除或更正走专门流程 |
| 科主任 | 本科室当前负责的患者 | 查看记录和诊疗进展；跨科室需会诊授权 |
| 患者 | 已可靠绑定到本人账号的记录 | 查看允许向患者开放的记录；不能更改医生记录 |
| 系统管理员 | 账号、科室、配置和审计元数据 | 管理权限，不因 `admin` 身份自动读取病例正文或影像 |
| 会诊医师 | 获批患者、目的及有效期内 | 按授予的只读/可写范围访问；过期自动撤销 |

科主任的范围以患者的当前主责科室或该科有效诊疗分配为准，不能简单按“上传医生属于此科”推断。调科、离职、转诊、撤销会诊后要立即重新计算访问权。紧急抢救访问可作为后续独立的“紧急授权”流程，要求理由、短有效期、强制审计和事后复核；MVP 不默认开放。

## 数据与服务设计

1. **组织和授权表**：新增 `departments`、`department_memberships`、`patient_care_assignments`、`access_grants`。记录机构/科室、医师岗位、患者主责科室、诊疗团队成员、授权人、用途、起止时间及撤销时间。现有 `users.role` 保留粗粒度身份，不能单独决定病例访问。
2. **病历索引表**：新增 `clinical_records`，包含患者、可选检查 ID、类型、标题、上传者、版本、状态、受控存储键、大小、MIME、SHA-256、创建时间。影像 `studies` 与附件共用患者授权服务，不复制患者所有权逻辑。
3. **文件服务**：采用私有存储；服务端生成存储键，不信任客户端路径或文件名。限制类型、大小、数量及解压体积；流式写入临时区、校验完整性后原子发布；失败时清理临时文件并回滚索引。下载经鉴权后流式返回，禁止暴露磁盘路径或永久公开 URL。
4. **统一授权函数**：实现 `can_view_patient`、`can_upload_record`、`can_download_record`、`can_manage_assignment`，并提供按授权范围过滤患者/检查列表的查询。DICOM、TICI、影像切片、AI 推理、结果、导出和附件接口全部调用同一策略；对象 ID 直接访问也必须校验。
5. **审计表**：记录登录、患者列表检索、病例查看、下载、上传、授权变更、拒绝访问和导出，至少保存操作者、对象、动作、时间、结果及请求关联 ID。日志不写病历正文、令牌或原始影像；审计查询另设权限。
6. **任务与前端**：大文件上传后返回任务 ID，后台解析 DICOM/TICI 并更新状态；前端增加“我的患者 / 本科室 / 会诊授权”视图、患者时间线、上传进度、授权申请和记录版本。列表按授权范围分页、搜索。

建议的首批 API：`GET /api/patients`、`GET /api/patients/{id}/records`、`POST /api/patients/{id}/records`、`GET /api/records/{id}`、`GET /api/records/{id}/download`、`POST /api/access-requests`、`POST /api/access-grants`、`DELETE /api/access-grants/{id}`、`GET /api/audit-events`。最终路径与当前 `/api/dicom`、`/api/tici` 的兼容方式在实现时定稿。

## 实施顺序

### 阶段 0：先封住现有越权入口

- 清点每个患者、检查、切片、TICI、AI 结果及导出端点；补一份权限矩阵和跨用户负例测试。
- 建立可回滚的数据库迁移；加入科室和诊疗关系。旧患者数据在迁移后先保持不可被普通医生读取，待管理员明确分配。
- 统一患者级读写策略，修复医生看全院、按 ID 越权、已有患者被上传者误关联等路径。
- 远程服务启动时强制配置随机密钥和初始管理员凭据，收紧 CORS；禁止中心服务执行未经审查的用户 `.pth` 文件。

**验收**：不同科且未授权的医生无法从列表、直接 ID、切片、TICI、AI 结果或导出获取同一患者数据；本科室科主任和已分配医师能访问授权范围；系统管理员默认无法读取病例内容。

### 阶段 1：病例上传与读取 MVP

- 建立病例索引、私有文件存储、上传任务及版本；支持 DICOM/TICI 和 PDF/图片等明确白名单附件。
- 接入服务端权限校验、患者时间线、范围内搜索、上传状态和失败重试。
- 每次读取、下载、上传和修改均写入审计；提供备份与恢复演练。

**验收**：跨科或撤销授权后直链下载失败；同一文件重复上传可识别；错误文件不留孤儿记录；备份可恢复索引与文件的一致版本。

### 阶段 2：跨科协作与管理

- 加入会诊申请、审批、限定用途与有效期、撤销、到期通知；提供科主任待审队列。
- 加入病历更正和版本追溯、导出申请及审计查询；患者可见范围单独配置。
- 再评估紧急授权、教学科研去标识化副本、统计看板和随访提醒。

**验收**：会诊授权只能访问指定患者与指定动作，到期和撤销立即生效；所有授权变更可追溯。

### 阶段 3：生产部署准备

- 医院内网 HTTPS、数据库和存储加密、密钥托管、最小权限服务账号、监控告警、容量和上传限流。
- 做权限回归、并发/大文件测试、安全审查和恢复演练；由合作机构确认数据处理目的、合法依据、告知/同意流程、保留期限及实际部署边界，再接入真实病例。

## 待确认的产品决策

- 一个患者能否同时由多个科室负责，以及转科后历史科室保留何种阅读权。
- “病历”首期包含哪些文件：影像、诊断报告、门诊/住院记录、医嘱，还是仅影像及附件。
- 患者账号是否在首期开放，以及哪些记录可以即时展示给患者。
- 中心服务落在医院内网、学校演示环境还是其他受控环境；演示环境只能使用合成或充分去标识化数据。

## 参考依据

- [《中华人民共和国个人信息保护法》](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)：医疗健康信息属于敏感个人信息；处理前需明确目的、必要性、安全措施，并进行相应的影响评估。
- [《电子病历应用管理规范（试行）》](https://www.nhc.gov.cn/wjw/c100175/201702/90f3de8ae03d488cbddf509dc958f75b.shtml)：电子病历系统的人员身份标识和访问权限要求。
- [《关于进一步加强医疗机构电子病历信息使用管理的通知》](https://www.nhc.gov.cn/yzygj/c100068/202506/c68abee7c54b4651a774cd533761780b.shtml)：医疗机构对使用范围、目的、期限和外部服务商访问的管理要求。

本计划给出工程控制点；真实医疗场景的制度和合规方案需与合作医疗机构共同确定。
